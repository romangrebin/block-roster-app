# Scaffold Status

What's built and actually running vs. just designed, and what's left.

## Environment

Default Node (via `nvm`) is 18.20.4; Next.js 16.3.0 needs ≥20.9.0. `.nvmrc` pins `22.7.0` — **run `nvm use` before any `npm`/`next`/`tsc` command**, or things fail in confusing ways (e.g. `next typegen` silently not populating `.next/types/`).

## Before writing more app code

Read `node_modules/next/dist/docs/` — Next 16 has breaking changes from most training data (e.g. `middleware.ts` → `proxy.ts`, caught this way). Everything ported so far typechecks/lints clean, but that doesn't guarantee every App Router pattern used is still idiomatic.

## What's built

**Data layer**
- `lib/types.ts`, `lib/repository.ts` — domain types + per-entity repository interfaces (schema v3, `minimal-schema-proposal.md`).
- `lib/supabase-admin.ts` — service-role client, server-only, used exclusively by the repository/application layer.
- `lib/adapters/supabase.ts` — full `BlockRosterRepository` implementation. Only adapter that exists — `mock`/`json-file` are still deferred.
- `lib/db.ts` — the adapter selector, currently always returns the Supabase adapter.
- `lib/application.ts` — cross-table functions: `createBlock`, `registerResident` (email + optional unverified phone), `verifyContactMethod`, `approveResident`, `moveResidentOut` (approved→moved_out, resets `block_wide` contacts to `steward_only`, re-derives residence status; added 2026-09-08), `promoteResidentToSteward` (approved resident → active steward, via their verified contact method's `userId` — no invite/email round-trip; added 2026-09-08, replaces the old invite mechanism entirely), `resolveActiveSteward`, `resolveApprovedResident` (resolves a signed-in user to their approved resident row for a *specific* block, via every contact method they've ever verified), `listApprovedResidentBlocks` (the reverse — every block a user is an approved resident of, no block known ahead of time; powers the home page's "Your blocks" list for non-steward members), `getResidentDirectory` (approved residents + `block_wide` contacts only — the peer-safe view used at `/<code>`). `confirmResidentPresence` (annual reconfirmation) is deliberately not built — Roman's call, a steward tracks move-outs manually for now.
- `lib/blockCode.ts` — the community-code generator/validator: default is now `adjective-animal-number` (e.g. `curious-otter-42`, ~200,000 combinations — changed 2026-09-08 from a random alphanumeric string, per Roman: something you can actually say out loud; the number suffix was added the same day once word-word alone (~2,000) turned out too small given the code also has to resist enumeration, not just collide rarely — see the file's own doc comment), steward-editable vanity slug, reserved-word denylist (`admin`, `api`, `blocks`, etc. — anything that'd collide with a real top-level route).
- `lib/csv.ts` — minimal CSV serialization (quotes only when needed, escapes internal quotes). Used by the roster export route, added 2026-09-08.
- `lib/mapStyle.ts` — the shared CARTO/OSM basemap style (pulled out of `DrawableMap.tsx` so `ResidenceMapPicker.tsx` isn't a second copy), `centroidOf()`, and `boundsOf()` (turf `buffer` + `bbox`, small padding) — the latter drives both the initial view and the pan restriction on any map drawing/picking *within* an existing boundary (residence shapes). Added 2026-09-08.
- `lib/overpass.ts` — `suggestAddressesWithinBoundary()`, a free (no key) OSM Overpass query for addresses inside a drawn boundary, each with a `shape` when OSM has that address tagged directly on a closed building `way` (`out geom`, not `out center` — needed the actual node ring, not just a centroid). Verified against a real test boundary before building on it: 27 addresses found in Minneapolis, every one a shaped way, not just a point. Added 2026-09-08. **Same day, reliability pass**: Roman hit 6-7 straight "Couldn't reach OpenStreetMap" failures — traced to `overpass.kumi.systems` (the only endpoint at the time) actively rate-limiting (HTTP 429), most likely from repeated dev-time testing off the same IP. Now tries two public mirrors in order, falling through on any failure (timeout, non-2xx, network error): `overpass-api.de` first, then `overpass.kumi.systems` — reordered after confirming via direct curl that `-api.de` was healthy (200) while `kumi.systems` was still 429'ing, so trying the known-bad one first on every request would've just wasted a round-trip. Client-side timeout per attempt raised 15s→25s (kept just above the query's own `[timeout:20]` so a slow-but-alive server gets a real chance before being aborted). Loading-state copy now reads "Looking for addresses within your community boundary…" (was "…near your boundary…", matching the button copy from the prior pass).

**Auth**
- `lib/supabase-browser.ts`, `lib/supabase-server.ts` (both a Route Handler client and a `cookies()`-based Server Component client), `lib/auth.ts` (`getUser`/`getUserFromServerComponent`), `app/api/auth/callback/route.ts`, `components/AuthButton.tsx` — magic-link auth, same mechanism for stewards and residents alike (added 2026-09-07; used to be steward-only, see `components/AuthButton.tsx`'s history for the old resident-never-signs-in framing).
- `proxy.ts` (repo root) refreshes the session cookie every request.
- `lib/admin.ts` — a separate, much smaller gate: `isAdmin(email)` checks the `ADMIN_EMAILS` env var. Not a role in the data model, deliberately just an allowlist for a one-person tool.

**API routes**
- `POST /api/blocks`, `PATCH /api/blocks/[id]` (steward-gated — code/public blurb/private notes/`residentExportEnabled`), `GET /api/blocks/[id]/export` (CSV — steward always, approved resident only if `residentExportEnabled`; added 2026-09-08), `POST /api/blocks/[id]/residences` (one label per call), `PATCH`/`DELETE /api/residences/[id]` (steward-gated — rename/delete, `PATCH` also accepts `shape`, area-capped at `MAX_PARCEL_AREA_KM2`; added 2026-09-08), `PATCH /api/residences/[id]/nickname` (any approved resident of that residence, or a steward; added 2026-09-09), `POST /api/residences/[id]/register` (public — name, email, optional phone), `POST /api/residents/[id]/approve`, `POST /api/residents/[id]/promote` (steward-gated), `POST /api/residents/[id]/move-out` (steward-gated), `DELETE /api/residents/[id]` (steward-gated, pending-only — removes an abandoned/mistaken registration; added 2026-09-09), `PATCH /api/residents/[id]/blurb` (ownership-checked — a resident editing their own blurb; added 2026-09-08), `PATCH /api/contact-methods/[id]/visibility` (ownership-checked — a resident narrowing/widening their own contact; added 2026-09-08), `DELETE /api/admin/blocks/[id]` (admin-gated).

**Design system** (added 2026-09-08, inspired by — not copied from — local-block-app's look, per Roman)
- `app/globals.css` — Tailwind v4 `@theme` tokens: warm parchment background (`--color-bg`), white cards (`--color-surface`), a clay/terracotta accent (`--color-accent`, distinct from local-block-app's teal — a deliberate choice so this doesn't just read as reused branding), `--color-ink`/`--color-muted` text tones, `--color-border`. Serif (Lora) headings over sans (Manrope) body, both via `next/font/google` in `app/layout.tsx` — replaced the default Geist pairing. Buttons/badges are `rounded-full` (pill), cards `rounded-2xl`, primary CTAs carry a terracotta-tinted shadow instead of a gray one. No dark-mode support (the old scaffold's unused media-query override was dropped along with it).

**2026-09-09, thirteenth pass — list overflow fix, Edit/Delete gated on selection, shape-save bug root-caused and fixed, a real data-model gap**: full writeup in `notes/ux-feedback.md`. Popup's status line dropped entirely (Vacant was the last one left). **The shape-save bug (four reports total) is now root-caused and fixed**: diagnostic logging (added, then removed once confirmed) showed the save Effect in `ResidencesOverviewMap` reading `pendingShape: null`/`editingResidenceId: null` despite `ResidenceControls` having correctly handed off the save moments earlier. Cause: calling `setState` synchronously *during render* (as this file's whole "render-time comparison instead of an Effect" pattern does throughout) makes React immediately re-invoke the component function right then — not just schedule a future render the way an Effect-triggered update would. The `editShapeCommand` render-time reset nulls `pendingShape`/`editingResidenceId` to end the edit session, and the save Effect further down the *same* render captures its closure from that re-invocation, after the null. Every other use of this pattern in the file happened to be safe (nothing downstream needed the pre-reset value); this was the one spot that did. Fixed with `pendingEditSnapshotRef`, a ref mirroring the *last non-null* shape/residenceId via a guarded Effect (skips whenever both have just been reset to null) — not written during render (a first attempt at that tripped this repo's "Cannot access refs during render" lint rule). Also fixed, but not confirmed as related: `ResidencesSection` switching between a `<div>` and a `<span>` at the same tree position depending on selection, which forces React to unmount/remount `ResidenceControls` (and lose its `editing` state) on any incidental `selectedResidenceId` change. `tsc`/lint clean. **Confirmed fixed by Roman same day** ("It worked!").
